## 集群

### 数据分布

* 数据分布理论，分布式数据库的核心问题是如何将整个数据集按照分区规则映射到多个节点上，使每个节点负责整体数据的一个子集。常见的分区规则包括哈希分区和顺序分区。
  * 哈希分区：具有良好的离散性，数据分布与业务无关，但无法顺序访问。这是```Redis Cluster```采用的方式。
  * 顺序分区：数据分布与业务相关，支持顺序访问，但容易产生数据倾斜。

  针对哈希分区，书中介绍了三种常见的规则：

    * 节点取余分区：
      * 使用 ```hash(key) % N（N为节点数）```计算映射关系。
      * 优点：实现简单。
      * 缺点：当节点数量变化（扩容或收缩）时，映射关系需要重新计算，会导致大规模的数据迁移。通常建议采用翻倍扩容的方式以减少迁移量。

      ![](https://raw.githubusercontent.com/Garden12138/picbed-cloud/main/redis/redis_dev_maintenance_37.png)

    * 一致性哈希分区：
      * 为每个节点分配一个```Token```并构成一个哈希环（范围0~2 ^ 32-）。数据根据```key```的哈希值顺时针找到第一个大于等于该值的```Token```节点。
      * 优点：增减节点只影响邻近节点。
      * 缺点：节点较少时容易分布不均；增减节点会造成部分数据无法命中，更适合缓存场景。

      ![](https://raw.githubusercontent.com/Garden12138/picbed-cloud/main/redis/redis_dev_maintenance_38.png)

    * 虚拟槽分区：
      * 这是对一致性哈希的改进，它使用分散度良好的哈希函数将数据映射到一个固定范围的整数集合中，这些整数被称为槽（```slot```）。
      * 槽是集群内数据管理和迁移的基本单位。

      ![](https://raw.githubusercontent.com/Garden12138/picbed-cloud/main/redis/redis_dev_maintenance_39.png)

      ![](https://raw.githubusercontent.com/Garden12138/picbed-cloud/main/redis/redis_dev_maintenance_40.png)

* ```Redis```数据分区，```Redis Cluster```采用了虚拟槽分区，其特点如下：
  * 槽的范围：所有的键根据哈希函数映射到 0~16383 整数槽内。
  * 计算公式：```slot = CRC16(key) & 16383```。
  * 管理方式：每一个节点负责维护一部分槽以及槽所映射的键值数据。
  * 核心优势：
    * 解耦了数据和节点的关系，简化了节点扩容和收缩的难度。
    * 节点自身维护槽的映射关系，无需客户端或代理服务维护元数据。
    * 支持节点、槽、键之间的映射查询，便于数据路由和在线伸缩。

* 集群功能限制，由于```Redis Cluster```r是分布式架构，相比单机模式在功能上存在一些限制，开发人员需要规避这些“坑”：
  * ```Key```批量操作限制：如 ```mset```、```mget``` 等，目前只支持具有相同```slot```值的```key```执行批量操作。
  * 事务操作限制：只支持多```key```在同一节点上的事务操作，跨节点事务无法使用。
  * 数据粒度限制：```Key```是数据分区的最小粒度，不能将一个巨大的键值对象（如非常大的hash或list）映射到不同的节点。
  * 数据库空间限制：单机支持16个数据库，而集群模式下只能使用一个数据库空间，即 ```db0```。
  * 复制结构限制：复制结构只支持一层，即从节点只能复制主节点，不支持嵌套的树状复制结构。

### 搭建集群

* 准备节点，搭建```Redis```集群通常至少需要6个节点（3主3从），以保证集群完整且具备高可用性。
  * 核心配置：每个节点必须开启集群模式，即在配置文件中设置 ```cluster-enabled yes```。
  * 集群配置文件：通过 ```cluster-config-file``` 关联一个自动生成的配置文件（如 ```nodes-6379.conf```），用于记录集群状态（节点```ID```、槽映射等），严禁手动修改此文件。
  * 节点```ID```：节点启动后会生成一个唯一的40位16进制字符串作为节点```ID```。与运行```ID```不同，节点```ID```在集群初始化后会持久化到配置文件中，重启也不会改变。
  * 启动状态：初始启动时，每个节点都是独立的，互不感知，且处于下线状态，因为此时还没有分配任何槽。

* 节点握手，是指运行在集群模式下的节点通过```Gossip```协议彼此通信，最终感知对方并组成集群的过程。
  * 操作命令：客户端在任一节点执行 ```cluster meet {ip} {port}``` 发起握手。
  * 通信过程：
    * 发起节点在本地创建目标节点信息对象，发送 ```meet``` 消息。
    * 目标节点接收消息并回复 ```pong``` 消息。
    * 双方建立周期性的 ```ping/pong``` 消息 通信。
  * 状态同步：只需对集群内所有节点执行 ```meet``` 操作，握手信息就会通过 ```Gossip``` 协议在整个集群内传播，使所有节点最终彼此感知。此时集群结构初步建立，但仍处于 ```fail``` 状态。

    ![](https://raw.githubusercontent.com/Garden12138/picbed-cloud/main/redis/redis_dev_maintenance_42.png)

* 分配槽，```Redis```集群将所有数据映射到 16384个槽（```slot```）中。只有当这16384个槽全部指派给在线的主节点后，集群状态才会变为 ```ok```。
  * 指派命令：使用 ```cluster addslots {slot}``` 命令为节点分配槽。通常建议将16384个槽平均分配给所有主节点。
  * 上线状态：当所有槽分配完毕，执行 ```cluster info``` 可看到 ```cluster_state:ok```。
  * 设置从节点：为保证高可用，需使用 ```cluster replicate {nodeId}``` 命令。该命令在从节点上执行，指定其要复制的主节点```ID```。从节点会复制主节点的槽信息及数据，完成高可用架构部署。

* 使用 ```redis-trib.rb``` 快速搭建，由于手动搭建步骤繁琐且易出错，```Redis```官方提供了基于```Ruby```实现的管理工具 ```redis-trib.rb```。
  * 环境准备：需要安装 ```Ruby``` 环境及 ```redis``` 依赖包。
  * 创建集群：
    * 使用命令：```redis-trib.rb create --replicas 1 {host1:port1} ... {hostN:portN}```。
    * ```--replicas 1``` 表示为每个主节点分配一个从节点。
  * 自动化流程：该工具会自动完成节点握手、槽分配以及主从关系建立的整个流程，极大简化了运维成本。
  * 完整性检查：搭建完成后，可使用 ```redis-trib.rb check {ip:port}``` 检查集群所有槽是否已正确覆盖。
