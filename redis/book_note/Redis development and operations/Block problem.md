## Redis 阻塞

### 发现阻塞

* ```Redis```采用单线程架构，一旦发生阻塞，所有的读写操作都会受到影响。主要从应用方感知、定位异常节点以及监控系统三个维度及时感知并定位```Redis```的阻塞问题。

* 应用方感知：异常统计与报警，当```Redis```出现阻塞时，线上应用服务通常是最先感知到的。
  *   **现象：** 应用方会收到大量的```Redis```超时异常。例如，使用```Java```客户端```Jedis```时，会频繁抛出 ```JedisConnectionException``` 异常。
  *   **监控做法：**
      *   在应用方代码中加入**异常统计**，并设置报警阈值（如一分钟内超过10个异常即触发报警），通过邮件、短信或微信通知开发人员。
      *   **利用日志系统：** 为了避免在代码各处重复编写监控逻辑，建议借助日志系统（如Java的logback或log4j）。
      *   **自定义Appender：** 开发人员可以自定义一个日志```Appender```（如 `RedisAppender`），专门收集```Redis```相关的错误日志，利用 `AtomicLongMap` 等工具进行并发计数，并在达到阈值时触发报警逻辑。这种方式对业务代码侵入性小，且易于维护。

* 快速定位异常节点，在应用方加入异常监控后，面临的一个实际问题是：**如何判断是哪一个Redis节点出现了问题**。
  *   **现有痛点：** 绝大多数```Redis```客户端类库在抛出超时异常时，并不会附带目标节点的```IP```和端口（```Port```）信息。在操作```Redis```集群或多节点环境时，这会导致开发人员无法快速定位故障点。
  *   **解决方案：**
      *   **修改客户端源码：** 以```Jedis```为例，可以修改其 `Connection` 类下的 `connect`、`sendCommand` 和 `readProtocolWithCheckingBroken` 等核心方法。
      *   **捕获并打印信息：** 在这些方法中专门捕获异常，并从底层连接信息中提取目标节点的```IP```和端口，将其打印在异常堆栈或日志中。这能极大地辅助运维人员快速锁定有问题的```Redis```实例。

* 借助监控系统发现阻塞，除了应用方的被动感知，建立完善的**Redis监控系统**是主动发现阻塞的关键。
  *   **关键指标监控：** 一个可靠的监控系统需要覆盖以下关键指标：
      *   **命令耗时与慢查询：** 监控是否有耗时较长的命令在执行。
      *   **持久化阻塞：** 监控```RDB```快照或```AOF```重写是否引起了阻塞。
      *   **连接拒绝：** 监控是否因为达到最大连接数而拒绝请求。
      *   **硬件资源：** 包括```CPU```、内存、网络```IO```、磁盘```IO```的使用率是否过载。
  *   **工具推荐：** 书中推荐了作者团队开源的 **CacheCloud** 系统，该系统内部的统计监控模块能够全方位识别```Redis```运行期的异常指标，辅助快速定位问题。

* 总结
  * 发现阻塞的核心在于**“内外结合”**：对内通过完善的监控系统时刻盯防```Redis```的运行指标；对外通过应用方的日志异常统计及时捕获超时反馈，并优化客户端以确保能够快速指认出故障节点。

### 内在原因

* 由于```Redis```采用单线程架构处理读写请求，任何内部操作导致的延迟都会直接影响系统的吞吐量和稳定性。

* ```API```或数据结构使用不合理，这是导致```Redis```阻塞最常见的原因之一。虽然```Redis```命令通常执行极快，但如果对大对象执行高复杂度的命令，必然会产生延迟。
  *   **问题核心**：在包含上万个元素的集合上执行复杂度为 ```O(n)``` 或更高的命令（如 `hgetall`、`smembers`、`keys`、`sort` 等）。
  *   **如何发现**：
      *   **慢查询日志**：使用 `slowlog get {n}` 命令获取最近的慢查询记录。建议将线上实例的慢查询阈值（`slowlog-log-slower-than`）设置为**1毫秒**，以便及时发现隐患。
      *   **大对象分析**：利用 `redis-cli --bigkeys` 工具扫描集群中的大对象，识别出内存占用过大或元素过多的键。
  *   **优化建议**：
      *   **修改命令**：用低复杂度的命令代替，例如用 `hmget` 代替 `hgetall`，严禁在线上使用 `keys` 命令。
      *   **拆分大对象**：将大对象拆分为多个小对象，防止单次操作处理过多数据（如按时间维度拆分好友集合）。

* ```CPU```饱和问题，```CPU```饱和是指```Redis```进程将单核```CPU```使用率跑到了接近100%，导致无法处理更多命令。
  *   **识别方法**：通过 `top` 命令查看```Redis```进程的```CPU```占用，并配合 `redis-cli --stat` 实时监控每秒的请求量（```OPS```）。
  *   **两种典型场景**：
      *   **高并发压力**：当单机```OPS```达到极限（如每秒处理6万+请求）时，单靠命令优化效果有限，此时需要通过**集群化水平扩展**来分摊压力。
      *   **过度内存优化导致的低效**：这是一种较隐蔽的场景。为了节省内存，如果过度放宽 `ziplist` 的使用条件（例如将 `hash-max-ziplist-entries` 设置得过大），会导致原本 ```O(1)``` 的操作退化为 ```O(n)```，极大消耗```CPU```资源。
  *   **监控工具**：查看 `info commandstats` 统计信息，分析命令的平均耗时。如果发现 ```O(1)``` 命令（如 `hset`）的平均耗时远超正常值（如达到百微秒级），则可能存在过度压缩编码的问题。

* 持久化相关的阻塞，持久化操作虽然通常在子进程中进行，但在特定阶段仍会阻塞主线程。
  *   **fork阻塞**：
      *   在执行```RDB```快照或```AOF```重写时，主线程需要调用 `fork` 创建子进程。虽然不复制物理内存，但需要**复制内存页表**。
      *   **风险**：对于内存很大的实例（如超过```10GB```），`fork` 操作可能耗时秒级，导致主线程在此期间无法响应任何命令。可通过 `info stats` 中的 `latest_fork_usec` 指标查看最近一次 `fork` 的耗时。
  *   **AOF刷盘阻塞**：
      *   当开启```AOF```且配置为 `everysec`（每秒同步）时，```Redis```使用后台线程执行 `fsync`。如果硬盘压力过大导致 `fsync` 超过2秒未完成，为了数据安全，主线程会**主动阻塞**直到同步完成。
      *   **识别**：查看```Redis```日志中的```“Asynchronous AOF fsync is taking too long”```警告，或监控 `info persistence` 中的 `aof_delayed_fsync` 指标。
  *   **HugePage写操作阻塞**：
      *   如果操作系统开启了**透明大页（THP）**，由于写时复制（```copy-on-write```）机制，每次写命令引起的内存页复制单位会从```4KB```放大到```2MB```（512倍），这会显著拖慢写操作的执行速度，导致大量写操作变慢。

* 总结：
  * 解决内在阻塞问题的核心思路在于：**合理选择数据结构与命令、监控关键性能指标、避免过度内存优化，并针对持久化和系统配置进行深度调优**。

### 外在原因

* 是非```Redis```自身逻辑或配置不当，而是由外部运行环境引发的问题。

* ```CPU```竞争，主要体现在两个方面：**进程竞争**和**绑定CPU**引起的问题。
  *   **进程竞争**：```Redis```是典型的**CPU密集型应用**，其高性能高度依赖于单线程对```CPU```的占有。因此，**不建议将Redis与其他多核CPU密集型服务部署在一起**。当其他进程过度消耗```CPU```资源时，会严重影响```Redis```的吞吐量。可以通过`top`或`sar`等系统命令定位```CPU```消耗的具体进程，并据此调整服务部署结构。
  *   **绑定CPU的问题**：为了降低```CPU```频繁上下文切换的开销，运维人员常会将```Redis```进程绑定到特定的```CPU```核心上。虽然这在平时是有效的优化，但在**RDB或AOF重写期间**会产生严重副作用。
      *   此时```Redis```父进程会创建子进程，由于父子进程共享绑定关系，它们将强制在同一个```CPU```核心上竞争。
      *   子进程在重写时的```CPU```使用率通常在90%以上，这会导致父进程无法获得足够的```CPU```时间片来响应命令，严重影响稳定性。
      *   **建议**：对于开启了持久化或参与复制的主节点，不建议进行强制的```CPU```绑定。

* 内存交换，对```Redis```来说是**致命的**，因为```Redis```保证高性能的前提是所有数据都在内存中。
  *   **危害**：如果操作系统将```Redis```使用的内存页换出到硬盘，由于硬盘读写速度比内存慢几个数量级，会导致```Redis```性能急剧下降甚至僵死。
  *   **识别方法**：
        *  通过`info server`获取```Redis```进程号（`process_id`）。
        *  查询`/proc/{process_id}/smaps`文件中的`Swap`字段。如果交换量大部分为```0KB```或极个别为```4KB```，则属正常；若数值较大则说明存在明显的内存交换。
  *   **预防措施**：
      *   保证机器有充足的可用物理内存。
      *   **必须设置Redis的最大可用内存（`maxmemory`）**，防止其内存失控增长。
      *   降低系统使用```Swap```的优先级，例如将`swappiness`设置为10或更小（Linux 3.5以上版本建议设为1）。

* 网络问题，是引发```Redis```阻塞的高发点，主要包括连接拒绝、网络延迟和网卡软中断。
  * 连接拒绝
    *   **网络闪断**：通常由网络割接或带宽耗尽引起，需借助`sar -n DEV`等流量监控工具识别。
    *   **Redis连接数溢出**：```Redis```通过`maxclients`参数控制最大连接数（默认10,000）。若连接数超限，可通过`info stats`中的`rejected_connections`指标观察被拒绝的数量。
    *   **连接溢出（操作系统层面）**：
        *   **进程限制**：受系统`ulimit -n`限制，如果文件句柄数（```TCP```连接也占句柄）不足，```Redis```会限制`maxclients`的大小。建议将`ulimit -n`设为65535。
        *   **backlog队列溢出**：系统对特定端口的```TCP```连接有`backlog`队列。```Redis```默认值为511。如果系统`somaxconn`参数小于该值（通常默认128），在高并发下会造成连接拒绝。需要通过`echo 511 > /proc/sys/net/core/somaxconn`进行修改。
  * 网络延迟，取决于物理拓扑和带宽。
      *   **拓扑影响**：同物理机 > 同机架 > 跨机架 > 同机房 > 异地机房。建议尽量将客户端与```Redis```部署在同机房。
      *   **延迟测试**：可以使用`redis-cli`的`--latency`、`--latency-history`或`--latency-dist`工具进行持续的延迟统计测试。
      *   **带宽瓶颈**：频繁操作大对象（```bigkey```）容易打满千兆网卡带宽，需重点监控网卡流量。
  * 网卡软中断，在高流量场景下，如果单个网卡队列只能使用一个```CPU```核心处理，会导致该核心负载过高，即网卡软中断瓶颈。通过`top`命令观察`si`指标可以识别此类问题。```Linux```内核2.6.35以后支持的**RPS（Receive Packet Steering）**技术可以实现在软件层面模拟多队列网卡，从而利用多核```CPU```分摊中断压力。

* 总结
  * 在排查```Redis```阻塞问题时，如果确认不是内部```API```使用不当或持久化导致的，应依次检查**CPU是否存在竞争**、**内存是否发生了Swap**以及**网络链路和系统内核配置是否存在瓶颈**。
