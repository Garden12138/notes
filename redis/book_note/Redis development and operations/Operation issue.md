## 开发与运维的“陷阱”

### Linux配置优化

* 内存分配控制 (```vm.overcommit_memory```)
  * 背景：```Linux```内核为了运行更多程序，通常允许进程申请超过实际物理内存的内存空间（```Overcommit```机制）。
  * 陷阱：如果该参数设置为0（默认），内核会检查是否有足够的可用内存；如果没有，申请将失败。对于```Redis```而言，执行```bgsave```或```bgrewriteaof```时的```fork```操作可能会因为内存不足而失败，并在日志中报错```“Cannot allocate memory”```。
  * 优化建议：将 ```vm.overcommit_memory``` 设置为 1。这代表内核允许超量使用内存直到用完为止，从而保证```fork```操作在低内存条件下也能执行成功。
  * 最佳实践：同时为```Redis```设置合理的```maxmemory```，保证机器预留20%~30%的闲置内存。

* ```swappiness``` 参数优化
  * 背景：```swappiness``` (0-100) 决定了操作系统使用```swap```分区的倾向程度。值越高，使用```swap```的概率越高。
  * 陷阱：```Redis```的高性能依赖于全内存操作。一旦发生内存交换（```Swap```），磁盘```IO```会成为系统瓶颈，导致```Redis```性能急剧下降。
  * 优化策略（取决于内核版本）：
    * ```Linux```内核 < 3.5：建议设置为 0，宁愿触发```OOM killer```也不要使用```swap```。
    * ````Linux```内核 >= 3.5：建议设置为 1。这样既能最大限度避免使用```swap```，又能在极端情况下通过```swap```缓解压力，而不是直接被杀掉进程（3.5的新内核```swappiness=0```行为变得更极端，会让内核几乎不主动 ```swap```，从而导致```OOM```，导致其他进程也被杀掉）。
  * 监控方法：可以通过 ```free -m``` 查看总体情况，或通过 ```/proc/{pid}/smaps``` 查询具体```Redis```进程的```swap```使用量。

* 禁用透明大页 (```Transparent Huge Pages, THP```)
  * 背景：```THP```支持```2MB```的大内存页分配（普通页为4```KB```），初衷是减少```fork```速度。
  * 陷阱：在```fork```之后的写时复制 (```Copy-on-Write```) 期间，即使只修改了4```KB```数据，开启```THP```会导致必须复制整个2```MB```的大页。这会大幅增加重写期间的内存消耗，并导致写操作的慢查询延迟放大数百倍。
  * 优化建议：```Redis```在启动日志中会明确建议禁用此特性。应执行 ```echo never > /sys/kernel/mm/transparent_hugepage/enabled``` 进行禁用。

* ```OOM killer``` 权重调整 (```oom_adj```)
  * 背景：当内存不足时，```OOM killer```会根据进程权值杀掉部分用户进程。
  * 优化建议：为了防止```Redis```主进程被优先误杀，可以将```Redis```进程的 ```oom_adj``` 设置为较低的值（如 -17），从而降低其被杀掉的概率。
  * 提示：这只是辅助手段，合理的内存规划才是根本。在高可用架构下，有时“被杀掉”触发故障转移比“僵死”更好。

* 使用 ```NTP``` 进行时钟同步
  * 背景：```Redis Sentinel```和```Cluste```r涉及多台服务器。
  * 原因：虽然```Redis```不严格依赖时钟一致性，但如果服务器时钟不一致，会导致日志排查极其困难（例如分析故障转移的时序）。
  * 优化建议：建议每天或每小时定时同步一次```NTP```服务，确保集群内所有机器时间统一。

* 文件描述符限制 (```ulimit```)
  * 背景：```Redis```的每个客户端连接在```Linux```中都表现为一个文件句柄。
  * 陷阱：如果系统的 ```open files (ulimit -n)``` 设置太小（如默认的1024），即使```Redis```的 ```maxclients``` 设置很大，也会因为系统限制而被迫缩减最大连接数，并在日志中发出警告。
  * 优化建议：通常建议将 ```ulimit -n``` 设置为 65535 或至少大于 ```maxclients + 32```。

* ```TCP backlog``` 设置
  * 原因：```Redis```默认的 ```tcp-backlog``` 为511。如果```Linux```系统的 ```/proc/sys/net/core/somaxconn``` 小于此值，```Redis```启动时会警告无法强制执行该设置。
  * 优化建议：执行 ```echo 511 > /proc/sys/net/core/somaxconn```（或更高值）来匹配```Redis``配置，以应对高并发场景下的连接队列压力。

### flushall/flushdb误操作

* 缓存与存储的区别，误操作后的损失程度取决于```Redis```在业务架构中的角色：
  * 作为缓存使用：虽然数据可以从数据源（如```MySQL```）重新构建，但如果业务并发量很大，大量请求会直接打向后端数据库，造成缓存雪崩或穿透，给后端造成巨大的负载压力。
  * 作为存储使用：误操作可能导致重要配置、基础数据或业务核心数据丢失。如果没有提前做好业务降级或容错预案，可能会导致应用报错或页面空白，后果不堪设想。

* 借助```AOF```机制恢复，如果```Redis```开启了```AOF```持久化（```appendonly yes```），误操作后的恢复可能性较高：
  * 原理：执行```flush```命令后，该命令会被追加到```AOF```文件中（例如记录为```*1 $8 flushall```）。
  * 关键限制——```AOF```重写：如果在误操作后发生了```AOF```重写，```Redis```会遍历当前（已清空的）数据库生成新的```AOF```文件，从而覆盖掉包含旧数据的老文件，导致数据彻底丢失。
  * 应对建议：误操作后应立即调大```AOF```重写参数（```auto-aof-rewrite-percentage```和```auto-aof-rewrite-min-size```）以阻止自动重写，并严禁手动执行```bgrewriteaof```。
  * 恢复方法：通过编辑```AOF```文件，删除其中的```flushall/flushdb```相关操作记录，并使用```redis-check-aof```工具修复文件格式后即可尝试恢复。

* ```RDB```的变化与局限，```RDB```文件在误操作后的表现取决于配置：
  * 未开启自动策略：除非手动执行了```save/bgsave```或发生了主从全量复制，否则老```RDB```文件仍保存着误操作前的数据，可作为恢复源。严禁在误操作后手动执行```save```，否则会生成空快照覆盖原有数据。
  * 开启了自动策略：由于```flush```涉及键值数量通常很多，极易触发```RDB```的自动保存条件，导致```RDB```文件被清空，此时通过```RDB```恢复基本无望。
  * 缺点：```RDB```恢复速度虽快，但其实时性通常不如```AOF```，可能丢失最后一次备份至今的数据。

* 从节点的变化，```Redis```的从节点会实时同步主节点的```flush```命令。因此，从节点的数据也会被同步清除，其持久化文件（```RDB/AOF```）的变化与主节点完全一致，无法直接通过未操作的从节点找回数据。

* 快速恢复数据的演练，一旦发生误操作，可按照以下步骤进行抢救性恢复：
  * 防止```AOF```重写：快速通过```config set```命令将```auto-aof-rewrite-percentage```和```auto-aof-rewrite-min-size```修改为极大值（如1000%和1000亿字节），确保在修复完成前不发生重写。
  * 修改```AOF```文件：找到并删除```AOF```文件中末尾的```flushall```相关内容。
  * 重启```Redis```：重新启动服务器，```Redis```会加载修改后的AOF文件完成数据恢复。

* 预防措施，为了彻底规避此类“陷阱”，建议在运维层面采取以下措施：
  * 危险命令伪装：利用```rename-command```配置将```flushall```、```flushdb```、```keys```等危险命令重命名为复杂的随机字符串。
  * 环境隔离与权限：根据网络环境决定是否设置密码，并避免使用```root```用户启动```Redis```，防止攻击者通过```flushall```配合```RDB```特性篡改系统文件。
  * 定期备份：养成定期备份持久化数据的习惯，以挽回极端情况下的损失。

### 安全的Redis

* 攻击案例分析与教训。攻击者利用了```Redis```的特性，通过```config set dir```和```config set dbfilename```动态修改配置，并结合```RDB```持久化功能，将攻击者的公钥写入服务器的```/root/.ssh/authorized_keys```文件中，从而获取```root```登录权限。
易受攻击的```Redis```通常具有以下特征：
  * 拥有外网```IP```且默认端口（6379）对外开放。
  * 以```root```用户身份启动。
  * 未设置密码且```bind```配置允许任何```IP```访问（如0.0.0.0）。

* 安全设计的七个要点，为了保证```Redis```不仅高效稳定，且运行在安全的网络环境下，书中提出了以下七个维度的安全建议：
  * 完善密码机制 (```requirepass```)
    * 设置方法： 通过```requirepass```配置提供密码功能。
    * 访问方式： 客户端需使用```redis-cli -a {password}```连接，或在连接后执行```auth {password}```命令。
    * 运维建议：
      * 密码必须足够复杂（建议64字节以上），以防暴力破解。
      * 主从架构中，从节点必须配置```masterauth```以匹配主节点密码，否则同步会失效。
      * 需注意```auth```命令在网络中是以明文传输的。
  * 伪装危险命令 (```rename-command```)
    * 原理： ```Redis```支持将危险命令重命名为随机长字符串，防止误操作或恶意调用。
    * 建议伪装的命令： ```keys```（可能阻塞）、```flushall/flushdb```（清除数据）、```save```（阻塞）、```config```（管理员权限）、```shutdown```（停止服务）等。
    * 副作用与限制：
      * 一旦重命名，```AOF```或```RDB```文件中若包含旧命令将导致无法启动。
      * 某些依赖特定命令的组件（如```Sentinel```内部使用```config```）可能会失效。
      * 不支持```config set```动态修改，必须在启动前配置好。
  * 利用防火墙限制访问
    * 这是限制外网访问的“必杀技”。即便服务器有外网```IP```，也应通过防火墙（如```iptables```）仅允许特定```IP```范围访问```Redis```端口。
  * 正确配置 ```bind```
    * 常见误区： ```bind```并非指定允许访问的客户端```IP```网段，而是指定```Redis```监听哪块网卡。
    * 最佳实践：
      * 如果只供本机访问，应绑定回环地址127.0.0.1。
      * 如果机器有外网```IP```但仅限内网使用，应去掉外网网卡绑定。
      * ```Redis 3.2+``` 提供了保护模式 (```protected-mode```)，在未配置密码且未配置```bind```时，默认只允许本地连接。
  * 定期备份数据
    * 定期备份持久化数据（```RDB/AOF```）是一个良好的习惯，能在遭受攻击或误操作导致数据清理后挽回损失。
  * 修改默认端口
    * ```Redis```默认端口是6379。将其修改为非标准端口可以避开大部分针对该端口的自动化扫描和攻击程序。
  * 使用非```root```用户启动
    * ```root```用户权限过大。使用普通的非特权用户启动```Redis```服务，即使```Redis```被攻破，攻击者也难以直接获取系统级控制权（如修改```/root/.ssh```目录）。这也是许多主流服务（如```Hadoop、HBase、Jetty```）的共同建议。

### 处理bigkey

* ```bigkey``` 是指 ```key``` 对应的 ```value``` 所占用的内存空间比较大，或者包含的元素个数过多。通常分为以下两类：
  * 字符串类型：单个 ```value``` 值很大。一般认为超过 10```KB``` 即可称为 ```bigkey```（具体标准需结合业务的 ```OPS``` 来看）。
  * 非字符串类型：如哈希、列表、集合、有序集合，主要体现在其内部元素个数过多。

* ```bigkey``` 的三大危害，```bigkey``` 是 ```Redis``` 生产环境中的一颗“定时炸弹”，其危害主要体现在三个方面：
  * 内存空间不均匀：在 ```Redis Cluster``` 中，```bigkey``` 会导致数据在各个节点上的分布极度不均，造成某些节点内存压力过大。
  * 超时阻塞：```Redis``` 是单线程运行的。操作 ```bigkey```（如删除或全量获取）非常耗时，极易导致 ```Redis``` 主线程阻塞，进而引发客户端超时异常。
  * 网络拥塞：每次获取 ```bigkey``` 都会产生巨大的网络流量。例如，一个 1```MB``` 的 ```bigkey``` 若每秒被访问 1000 次，就会产生 100```0MB/s``` 的流量，这对千兆网卡（约 128```MB/s```）的服务器来说是毁灭性的。

* 如何发现 ```bigkey```，为了避免 ```bigkey``` 影响业务，开发和运维人员可以通过以下方式主动或被动地寻找它们：
  * 使用 ```redis-cli --bigkeys```：这是 ```Redis``` 自带的工具，可以统计并展示 ```bigkey``` 的分布情况。
  * 使用 ```debug object key``` 命令：通过该命令查看 ```serializedlength``` 属性，它表示 ```key``` 对应 ```value``` 序列化后的字节数。需要注意，这个值通常比实际内存占用偏小，且在元素过多时执行较慢，存在阻塞风险。
  * 主动检测（推荐）：利用 ```scan``` 命令渐进式地扫描所有键，配合 ```debug object``` 计算大小，并建立报警机制。为了降低对主节点的影响，建议在从节点上执行，或利用 ```Pipeline``` 提高效率。
  * 被动收集：在 ```Redis``` 客户端代码中加入逻辑，当命令执行超时或抛出异常时打印出对应的 ```key```，辅助排查。

* 如何优雅地删除 ```bigkey```，直接使用 ```del``` 命令删除元素过多的 ```bigkey``` 可能会导致长时间阻塞。根据数据结构的不同，应采取以下策略：
  * ```String``` 类型：通常 ```del``` 不会产生严重阻塞，但若值达到数十 ```MB``` 级别也需谨慎。
  * ```Hash/List/Set/ZSet``` 类型：禁止直接使用 ```del```。应使用对应的扫描命令（```hscan、ltrim、sscan、zscan```）分批次删除。
    * 示例（哈希删除）：先通过 ```hscan``` 每次获取 100 个 ```field```，再用 ```hdel``` 删除这些 ```field```，循环此过程直到全部删完，最后再 ```del``` 键本身。
  * 新版本特性：```Redis 4.0``` 以后支持 ```lazy delete```（惰性删除），可以使用 ```unlink``` 命令在后台非阻塞地释放内存。

* 最佳实践思路，在实际开发和运维中，应遵循以下思路来规避 ```bigkey``` 问题：
  * 合理设计数据结构：在开发初期就应评估数据规模，避免将 ```Redis``` 当作简单粗暴的存储使用。
  * 拆分 ```bigkey```：如果 ```bigkey``` 不可避免，考虑将其拆分为多个小的 ```key``` 分布到不同节点。
  * 避免全量获取：对于集合类对象，尽量使用 ```hmget``` 等局部获取命令，而不是 ```hgetall```。
  * 定期清理：建立长效的 ```bigkey``` 扫描机制，及时处理不再需要的庞大数据。

### 寻找热点key

* 热点```key```的背景与挑战

  热门新闻事件或商品往往会给系统带来巨大的流量。在```Redis```集群（如```Redis Cluster```）中，这些流量通常会集中在存储该热点```key```的特定节点上，造成整体流量不均衡，甚至导致个别节点```OPS```（每秒操作数）过大，超过```Redis```本身的承受能力。因此，寻找并处理热点```key```对开发和运维人员至关重要。

* 发现热点```key```的四种方案
  作者从距离```key```“由近到远”的角度提出了四种统计方案：

  ① 客户端方案（```Client```）
    * 实现原理：在客户端代码（如```Jedis```的```sendCommand```方法）中加入逻辑，利用全局字典（如```Guava```的```AtomicLongMap```）记录每个```key```的调用次数。
    * 优点：实现简单。
    * 缺点：内存泄露隐患：无法预知```key```的个数，字典可能无限膨胀。
    * 维护成本高：需要对各种语言的客户端都进行逻辑维护。
    * 视野局限：只能了解当前客户端的热点情况，无法实现规模化统计。

  ② 代理端方案（```Proxy```）
    * 实现原理：在```Twemproxy```、```Codis```等基于代理的分布式架构中，代理层是客户端与服务端的必经之路，最适合进行热点```key```的统计。
    * 优点：实现最系统、最方便。
    * 缺点：并非所有```Redis```架构都包含代理层，且会增加代理端的开发与部署成本。

  ③ ```Redis```服务端方案（```Server```）
    * 实现原理：利用```monitor```命令监控```Redis```执行的所有命令，并通过工具（如```Facebook```开源的```redis-faina```）解析输出结果，统计出热点```key```排行榜。
    * 优点：实现简单。
    * 缺点：
      * 性能风险：```monitor```命令在高并发下会导致Redis内存暴增并影响性能，仅适合短时间使用。
      * 统计局限：只能统计单个节点，集群模式下需手动汇总。

  ④ 机器抓包方案（```Network```）
    * 实现原理：在```Redis```服务器上对```TCP```数据包进行抓取，由于```Redis```通信遵循```RESP```协议，可以通过解析数据包（如利用```packetbeat```插件）完成统计。
    * 优点：对```Redis```客户端和服务端毫无侵入，是理论上最完美的方案。
    * 缺点：开发成本高，且仍需后期进行集群维度的统计汇总。

  四种方案对比总结： 
  
    | 方案 | 优点 | 缺点 | 
    | :--- | :--- | :--- | 
    | 客户端 | 实现简单 | 内存泄露隐患、维护成本高、无法跨客户端汇总 | 
    | 代理端 | 系统化、最方便 | 增加开发部署成本、不适用于无代理架构 | 
    | 服务端 | 实现简单 | ```monitor```影响性能、只能针对单节点 | 
    | 机器 | 无侵入、无影响 | 需要专业运维团队开发、部署成本高 |

* 解决热点```key```的三种思路
  
  找到热点```key```后，可根据业务场景选择以下方案：
    * 拆分复杂数据结构：如果热点```key```是二级数据结构（如```Hash```），且元素较多，可将其拆分为多个新的```key```分布到不同节点，以减轻单一节点的压力。
    * 迁移热点```key```：在```Redis Cluster```中，可以将热点```key```所在的```slot```单独迁移到一个负载较低的节点，但这会增加运维成本。
    * 本地缓存加通知机制：将热点数据存放在业务端的本地缓存（内存）中，其处理能力远超```Redis```。为保证数据一致性，可结合发布订阅机制在数据更新时通知各业务端清理本地缓存。
