## 缓存设计

### 缓存的收益和成本

* 缓存的基本架构，在传统的应用架构中，客户端通常直接调用存储层（如```MySQL```）。引入缓存后，架构变更为**“客户端-缓存层-存储层”**的模式。在这种模式下，绝大部分请求的数据应尽可能从缓存层获取，只有当缓存未命中时才访问存储层并回写缓存。

  ![](https://raw.githubusercontent.com/Garden12138/picbed-cloud/main/redis/redis_dev_maintenance_58.png)

* 缓存带来的收益，合理使用缓存可以为系统带来显著的性能提升：
  * 加速读写： 由于缓存通常是全内存运行的（如```Redis```、```Memcached```），其读写性能远强于以硬盘为基础的存储层（如```MySQL```）。这种高性能可以有效优化用户体验。以```Redis```为例，每秒可以完成数万次读写操作。
  * 降低后端负载： 缓存层可以分担后端的访问量，减少存储层执行复杂计算（如复杂的```SQL```联表操作或分组计算）的次数，从而保护后端数据源，防止其因高负载而崩溃。

* 缓存引入的成本，虽然收益巨大，但将缓存加入应用架构也会带来一些不可避免的问题和成本：
  * 数据不一致性： 缓存层和存储层之间存在数据同步的时间窗口，这会导致两层之间的数据在一段时间内不一致。不一致的程度取决于所选用的缓存更新策略。
  * 代码维护成本： 开发者需要编写额外的逻辑来处理缓存层和存储层之间的交互，这增加了业务代码的复杂度和维护难度。
  * 运维成本： 引入如```Redis Cluster```等分布式缓存系统后，无形中增加了运维人员管理集群、监控节点和处理故障的工作量。

* 典型使用场景，缓存主要适用于以下两类场景：
  * 开销大的复杂计算： 针对```MySQL```中一些耗时极长的操作（如大量联表或复杂统计），通过缓存结果，可以避免这些操作拖垮数据库，并能支持更高的并发。
  * 加速请求响应： 即使单条后端查询速度很快，依然可以利用```Redis```的高并发能力和批量操作（```Pipeline/mget```等）来进一步优化整个```IO```链的响应时间。

### 缓存更新策略

* ```LRU/LFU/FIFO``` 算法剔除
  * 使用场景： 主要用于缓存使用量超过预设最大值的情况。例如，当```Redis```的使用内存达到```maxmemory```上限时，会根据配置的```maxmemory-policy```策略对现有的数据进行剔除。
  * 一致性： 最差。因为清理哪些数据是由具体的算法（如最近最少使用```LRU```）决定的，开发人员无法精确控制，因此无法保证业务层面的数据一致性。
  * 维护成本： 低。开发人员通常只需要配置最大内存和对应的剔除策略即可，无需编写复杂的业务代码。

* 超时剔除
  * 使用场景： 通过给缓存数据设置过期时间（如```Redis```的```expire```命令），让其在到期后自动删除。这种策略适用于业务可以容忍一段时间内数据不一致的场景。例如，视频的描述信息可以容忍几分钟的延迟，但交易类业务则不适用。
  * 一致性： 较差。在缓存过期之前，如果真实数据源发生了变化，缓存层和存储层会存在一致性窗口。
  * 维护成本： 较低。只需在写入缓存时设置过期时间，并在数据失效后重新从数据源获取并回写缓存即可。

* 主动更新
  * 使用场景： 适用于对数据一致性要求极高的业务。在真实数据源更新后，立即通过某种机制（如消息系统）通知并更新缓存数据。
  * 一致性： 强。理论上能保持最高的一致性，但如果主动更新逻辑出错（如消息丢失），可能导致脏数据长时间存在，因此建议结合超时剔除策略作为补底方案。
  * 维护成本： 高。开发人员需要自己实现更新逻辑，并确保该操作的原子性和正确性。

* 三种策略对比总结

  | 策略 | 一致性 | 维护成本 |
  | :---: | :---: | :---: |
  | 算法剔除 | 最差 | 低 |
  | 超时剔除 | 较差 | 较低 |
  | 主动更新 | 强 | 高 |

* 最佳实践建议：
  * 对于一致性要求较低的业务： 建议配置最大内存限制（```maxmemory```）配合淘汰策略使用。
  * 对于一致性要求较高的业务： 建议采用超时剔除与主动更新相结合的方式。这样即使主动更新失效，也能通过过期时间确保脏数据最终会被删除。
