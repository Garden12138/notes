## 缓存设计

### 缓存的收益和成本

* 缓存的基本架构，在传统的应用架构中，客户端通常直接调用存储层（如```MySQL```）。引入缓存后，架构变更为**“客户端-缓存层-存储层”**的模式。在这种模式下，绝大部分请求的数据应尽可能从缓存层获取，只有当缓存未命中时才访问存储层并回写缓存。

  ![](https://raw.githubusercontent.com/Garden12138/picbed-cloud/main/redis/redis_dev_maintenance_58.png)

* 缓存带来的收益，合理使用缓存可以为系统带来显著的性能提升：
  * 加速读写： 由于缓存通常是全内存运行的（如```Redis```、```Memcached```），其读写性能远强于以硬盘为基础的存储层（如```MySQL```）。这种高性能可以有效优化用户体验。以```Redis```为例，每秒可以完成数万次读写操作。
  * 降低后端负载： 缓存层可以分担后端的访问量，减少存储层执行复杂计算（如复杂的```SQL```联表操作或分组计算）的次数，从而保护后端数据源，防止其因高负载而崩溃。

* 缓存引入的成本，虽然收益巨大，但将缓存加入应用架构也会带来一些不可避免的问题和成本：
  * 数据不一致性： 缓存层和存储层之间存在数据同步的时间窗口，这会导致两层之间的数据在一段时间内不一致。不一致的程度取决于所选用的缓存更新策略。
  * 代码维护成本： 开发者需要编写额外的逻辑来处理缓存层和存储层之间的交互，这增加了业务代码的复杂度和维护难度。
  * 运维成本： 引入如```Redis Cluster```等分布式缓存系统后，无形中增加了运维人员管理集群、监控节点和处理故障的工作量。

* 典型使用场景，缓存主要适用于以下两类场景：
  * 开销大的复杂计算： 针对```MySQL```中一些耗时极长的操作（如大量联表或复杂统计），通过缓存结果，可以避免这些操作拖垮数据库，并能支持更高的并发。
  * 加速请求响应： 即使单条后端查询速度很快，依然可以利用```Redis```的高并发能力和批量操作（```Pipeline/mget```等）来进一步优化整个```IO```链的响应时间。

### 缓存更新策略

* ```LRU/LFU/FIFO``` 算法剔除
  * 使用场景： 主要用于缓存使用量超过预设最大值的情况。例如，当```Redis```的使用内存达到```maxmemory```上限时，会根据配置的```maxmemory-policy```策略对现有的数据进行剔除。
  * 一致性： 最差。因为清理哪些数据是由具体的算法（如最近最少使用```LRU```）决定的，开发人员无法精确控制，因此无法保证业务层面的数据一致性。
  * 维护成本： 低。开发人员通常只需要配置最大内存和对应的剔除策略即可，无需编写复杂的业务代码。

* 超时剔除
  * 使用场景： 通过给缓存数据设置过期时间（如```Redis```的```expire```命令），让其在到期后自动删除。这种策略适用于业务可以容忍一段时间内数据不一致的场景。例如，视频的描述信息可以容忍几分钟的延迟，但交易类业务则不适用。
  * 一致性： 较差。在缓存过期之前，如果真实数据源发生了变化，缓存层和存储层会存在一致性窗口。
  * 维护成本： 较低。只需在写入缓存时设置过期时间，并在数据失效后重新从数据源获取并回写缓存即可。

* 主动更新
  * 使用场景： 适用于对数据一致性要求极高的业务。在真实数据源更新后，立即通过某种机制（如消息系统）通知并更新缓存数据。
  * 一致性： 强。理论上能保持最高的一致性，但如果主动更新逻辑出错（如消息丢失），可能导致脏数据长时间存在，因此建议结合超时剔除策略作为补底方案。
  * 维护成本： 高。开发人员需要自己实现更新逻辑，并确保该操作的原子性和正确性。

* 三种策略对比总结

  | 策略 | 一致性 | 维护成本 |
  | :---: | :---: | :---: |
  | 算法剔除 | 最差 | 低 |
  | 超时剔除 | 较差 | 较低 |
  | 主动更新 | 强 | 高 |

* 最佳实践建议：
  * 对于一致性要求较低的业务： 建议配置最大内存限制（```maxmemory```）配合淘汰策略使用。
  * 对于一致性要求较高的业务： 建议采用超时剔除与主动更新相结合的方式。这样即使主动更新失效，也能通过过期时间确保脏数据最终会被删除。

### 缓存粒度控制

* 核心问题定义，在实际开发中，以用户信息为例，如果```MySQL```中用户表有100个列，开发者面临两种选择：
  * 缓存全部列：将整行用户信息（所有属性）序列化后存入```Redis```。
  * 缓存部分重要列：仅筛选业务高频使用的属性进行缓存。

* 三个维度的对比分析，为了做出合理的决策，需要从通用性、空间占用和代码维护三个角度进行权衡：
  * 通用性 (```Universality```)：
    * 全部数据：通用性高。因为包含了所有属性，可以满足未来各种业务场景的需求。
    * 部分数据：通用性低。通常只针对当前业务逻辑设计，如果其他业务需要不同字段，则无法直接复用该缓存。
    * 实际现状：尽管全部数据更通用，但经验表明，很多应用在很长一段时间内其实只需要几个关键属性。
  * 空间占用 (```Space Occupancy```)：
    * 全部数据：占用空间大。这会带来三个具体问题：
      * 内存浪费：存储了大量可能永远不会被访问的冗余属性。
      * 网络流量开销：每次传输的数据量大，可能导致网络延迟增加，极端情况下会阻塞网络带宽。
      * ```CPU```开销：序列化和反序列化大对象时，会消耗更多的```CPU```资源。
    * 部分数据：占用空间小。能显著降低内存压力和网络带宽负担。
  * 代码维护 (```Code Maintenance```)
    * 全部数据：简单。开发逻辑直观，不需要在存取时筛选字段。
    * 部分数据：较为复杂。一旦业务需求发生变更，需要增加新字段，开发者必须修改业务代码，且通常还需要刷新/重构现有的缓存数据。

* 方案对比总结：

  | 数据类型 | 通用性 | 空间占用 (内存+网络) | 代码维护 |
  | :---: | :---: | :---: | :---: |
  | 全部数据 | 高 | 大 | 简单 |
  | 部分数据 | 低 | 小 | 较为复杂 |

### 穿透优化

* 缓存穿透的定义与过程，***缓存穿透是指查询一个根本不存在的数据，导致缓存层和存储层都不会命中***。
 在常规的缓存策略中，如果从存储层查不到数据，通常出于容错考虑不会将其写入缓存层。
 这就导致了整个过程分为以下三步：

  * 缓存层不命中。
  * 存储层不命中，且不将空结果写回缓存。
  * 返回空结果。

  在这种情况下，不存在的数据每次请求都要到存储层去查询，缓存失去了保护后端存储的意义。

  ![](https://raw.githubusercontent.com/Garden12138/picbed-cloud/main/redis/redis_dev_maintenance_59.png)

* 缓存穿透的危害与原因，缓存穿透会使后端存储负载加大，由于许多后端存储（如```MySQL```）不具备高并发性，大量空命中请求可能导致后端存储宕机。

  造成缓存穿透的基本原因通常有两个：
    * 自身业务代码或数据出现问题：例如由于逻辑错误导致查询不存在的键。
    * 恶意攻击、爬虫：攻击者故意制造大量不存在的```key```进行查询，造成存储层压力。

* 优化方案一：缓存空对象
  
  缓存空对象是指当存储层查询不命中后，仍然将一个空对象（或约定的空值）保留到缓存层中。之后再访问这个相同的数据时，请求会直接从缓存中获取，从而保护了后端数据源。

  ![](https://raw.githubusercontent.com/Garden12138/picbed-cloud/main/redis/redis_dev_maintenance_60.png)

  该方案存在的问题及对策：
    * 内存空间消耗：空值也做缓存，意味着缓存层需要存储更多的键。
      * 对策：针对这类数据设置一个较短的过期时间（例如5分钟），让其自动剔除。
    * 数据不一致：缓存层和存储层的数据在过期时间窗口内可能存在不一致。
      * 对策：如果存储层在此期间添加了该数据，可以利用消息系统或其他方式主动清除缓存中的空对象。
      
  示例代码逻辑：在从存储获取数据后，若发现为```null```，则使用```cache.setex(key, timeout, value)```设置一个较短的过期时间。

* 优化方案二：布隆过滤器拦截
  
  布隆过滤器拦截是在访问缓存层和存储层之前，将所有可能存在的key提前保存到布隆过滤器中。请求进入时，先经过布隆过滤器的拦截：
    * 如果布隆过滤器认为该```key```不存在，则直接返回，不再访问缓存和存储层。
    * 如果布隆过滤器认为该```key```可能存在，才允许继续后续流程。

  ![](https://raw.githubusercontent.com/Garden12138/picbed-cloud/main/redis/redis_dev_maintenance_61.png)

  适用场景与特点：
    * 适用于数据集大、数据相对固定、实时性要求低的场景。
    * 优势：缓存空间占用极少。
    * 劣势：代码实现和维护较为复杂。
    * 开发提示：可以利用```Redis```的**Bitmaps（位图）**来实现布隆过滤器。

* 两种方案的选择与对比
  
  根据源文件提供的对比表，开发人员应根据业务需求进行取舍：

    | 解决缓存穿透 | 适用场景 | 维护成本 |
    | :---: | :---: | :---: |
    | 缓存空对象 | 数据命中率不高、数据频繁变化、实时性要求高 | 代码维护简单，但需要更多缓存空间，存在数据不一致风险 |
    | 布隆过滤器 | 数据命中率不高、数据相对固定、实时性要求低 | 代码实现和维护较为复杂，缓存空间占用极少 |

### 无底洞优化

* “无底洞”现象的由来，“无底洞”（```No-Bottom Hole```）现象最早由```Facebook```的运维团队在2010年观察到。当时为了满足业务增长，```Facebook```向其```Memcache```集群投入了大量新节点，但发现集群性能不但没有提升，反而出现了下降。

  核心原因在于：
    * 键值分布与业务无关： 分布式缓存通常使用哈希函数将```key```随机映射到各个节点。
    * 批量操作的成本： 在单机环境下，批量操作（如```mget```）只需一次网络往返。但在分布式（如Redis Cluster）环境下，批量操作可能需要从多个节点获取数据，涉及多次网络操作。
    * 节点规模效应： 随着节点数增多，一次批量操作涉及的节点可能也越多，导致网络总耗时增加，且网络连接数的增多也会影响节点性能。

  总结来说，更多的节点不代表更高的性能，如果处理不当，投入的资源越多（节点越多），批量操作的延迟反而越高。

* 四种批量操作优化方案
为了优化分布式环境下的批量操作，降低网络往返次数是关键。书中提出了四种方案：

  * 串行命令 (```Serial Command```)
    * 实现机制： 客户端不考虑```key```的分布，直接对```n```个```key```循环执行```n```次```get```命令。
    * 时间复杂度： ```n```×网络时间+```n```×命令时间。
    * 优点： 编程实现最简单。
    * 缺点： 网络次数是```n```，对于大量```key```的操作延迟非常严重。
    
    ![](https://raw.githubusercontent.com/Garden12138/picbed-cloud/main/redis/redis_dev_maintenance_62.png)

  * 串行 ```IO (Serial I/O)```
    * 实现机制： 客户端利用```Redis Cluster```本地保存的```slot``` -> ```node```映射关系，将属于同一个节点的```key```进行归档。然后对每个节点子列表执行一次批量操作（如```mget```或```pipeline```）。
    * 时间复杂度： ```nodes```×网络时间+```n```×命令时间。
    * 优点： 编程相对简单，显著优于串行命令。
    * 缺点： 依然是串行执行，如果节点数较多，延迟仍会随之增加。

    ![](https://raw.githubusercontent.com/Garden12138/picbed-cloud/main/redis/redis_dev_maintenance_63.png)

* 并行 ```IO (Parallel I/O)```
  * 实现机制： 在串行```IO```的基础上，将最后一步发往各个节点的请求改为多线程并行执行。
  * 时间复杂度： ```max```(```node```网络时间)+```n```×命令时间。
  * 优点： 网络时间变为O(1)，在大规模集群下性能表现最好。
  * 缺点： 编程复杂度较高，多线程下的问题定位可能较难。

  ![](https://raw.githubusercontent.com/Garden12138/picbed-cloud/main/redis/redis_dev_maintenance_64.png)

* ```hash_tag``` 实现
  * 实现机制： 利用```Redis Cluster```的```hash_tag```功能，强制将多个相关的```key```分配到同一个槽（```slot```），从而使其位于同一个节点上。
  * 时间复杂度： 1×网络时间+```n```×命令时间。
  * 优点： 性能最高，网络IO次数为O(1)。
  * 缺点： 业务维护成本高，极易造成数据倾斜（某些节点压力过大）。

  ![](https://raw.githubusercontent.com/Garden12138/picbed-cloud/main/redis/redis_dev_maintenance_65.png)

* 方案对比总结分析书中通过 表11-4 对这四种方案进行了直观对比：
  
  | 方案 | 优点 | 缺点 | 网络```IO```次数 |
  | :---: | :---: | :---: |
  | 串行命令 | 编程简单 | 大量```keys```请求延迟严重 | ```O(keys)``` |
  | 串行 ```IO``` | 编程简单 | 大量```node```延迟严重 | ```O(nodes)``` |
  | 并行 ```IO``` | 延迟取决于最慢节点 | 编程复杂，定位难 | ```O(max_slow(nodes))``` |
  | ```hash_tag``` | 性能最高 | 易出现数据倾斜 | ```O(1)``` |
