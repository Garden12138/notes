## 理解内存

### 内存消耗

* 了解```Redis```内存使用的各个组成部分，这是高效利用```Redis```内存、进行管理和优化的基础。

* 内存使用统计，要理解内存消耗，首先需要掌握```Redis```自身提供的统计数据。通过执行 **`info memory`** 命令可以获取内存相关的各项指标。其中需要重点关注以下指标及其关系：
  *   **`used_memory`**：由```Redis```分配器分配的内存总量，即内部存储的所有数据的内存占用量。
  *   **`used_memory_rss`**：从操作系统角度显示的```Redis```进程占用的**物理内存总量**。
  *   **`mem_fragmentation_ratio`**：内存碎片率，计算公式为 `used_memory_rss / used_memory`。
      *   **当比值 > 1 时**：说明存在内存碎片。如果两者相差很大，说明**碎片率严重**。
      *   **当比值 < 1 时**：通常说明操作系统将```Redis```内存**交换（Swap）到了硬盘**。由于硬盘速度远慢于内存，这会导致```Redis```性能急剧下降甚至僵死。

* 内存消耗划分，```Redis```进程内的内存消耗主要划分为四个部分：**自身内存、对象内存、缓冲内存和内存碎片**。
  *   **自身内存**：```Redis```空进程自身消耗的内存非常少，通常 `used_memory_rss` 在```3MB```左右，`used_memory` 在800KB左右，基本可以忽略不计。
  *   **对象内存**：这是**内存占用最大的一块**，存储着用户的所有数据。```Redis```所有数据都是```key-value```类型，每次创建键值对至少创建两个对象：```key```对象和```value```对象。
      *   **键对象**：均为字符串类型，应避免使用过长的键以减少内存浪费。
      *   **值对象**：包含五种基本类型及基于其实现的扩展类型。每种类型根据使用规模不同，内存占用也不同。
  *   **缓冲内存**：主要包括以下三类：
      *   **客户端缓冲**：所有接入```Redis```的```TCP```连接的输入输出缓冲。
          *   *普通客户端*：一般消耗可忽略，但在大量慢连接或大数据输出（如执行 `monitor` 命令）时可能导致内存飙升。
          *   *从客户端*：用于主从复制。主从间网络延迟高或挂载从节点过多时，这部分消耗会很大。
          *   *订阅客户端*：发布订阅功能中，若消息生产快于消费速度，输出缓冲区会积压溢出。
      *   **复制积压缓冲区**：```Redis 2.8```后提供的可重用固定大小缓冲区（默认```1MB```），用于实现部分复制，建议设置较大（如```100MB```）以有效避免全量复制。
      *   **AOF缓冲区**：用于在```AOF```重写期间保存最近的写入命令。其大小取决于重写时间和写入量，通常占用很小。
  *   **内存碎片**：```Redis```默认采用 **jemalloc** 内存分配器。分配器为了管理方便，通常采用固定范围的内存块进行分配。
      *   **产生原因**：保存的对象大小与分配器提供的块大小不匹配；频繁的更新操作（如 `append`）；大量过期键删除后释放的空间无法充分利用。
      *   **解决方式**：数据尽量对齐（如使用数字或固定长度字符串）；利用哨兵或集群架构进行**安全重启**以重新整理内存。

* 子进程内存消耗，子进程内存消耗主要指执行 **RDB或AOF重写** 时，```Redis```创建子进程产生的内存开销。
  *   **写时复制（Copy-on-Write, COW）机制**：理论上子进程需要一倍物理内存，但```Linux```通过```COW```机制让父子进程共享物理内存页。只有当父进程处理写请求修改页面时，才会复制出一份副本，因此实际消耗取决于期间的写入命令量。
  *   **Transparent Huge Pages（THP）的危害**：
      *   ```THP```会将内存页单位从```4KB```变为```2MB```。
      *   **影响**：虽然能降低```fork```速度，但由于内存页变大，```COW```期间的内存拷贝量会放大512倍，导致**严重的内存消耗**和写操作慢查询。
      *   **建议**：在生产环境中应当**禁用THP**（执行 `echo never > /sys/kernel/mm/transparent_hugepage/enabled`）。
  *   **内核配置建议**：设置 `vm.overcommit_memory = 1`，允许内核分配所有物理内存，防止```Redis```因系统剩余内存不足而导致```fork```失败。

### 内存管理

* 设置内存上限，```Redis```通过 `maxmemory` 参数限制最大可用内存。设置此上限的主要目的包括：
  *   **用于缓存场景**：当内存使用达到上限时，触发删除策略（如```LRU```）释放空间。
  *   **防止物理内存耗尽**：避免```Redis```占用过量内存导致操作系统出现性能问题。

  **注意点**：`maxmemory` 限制的是```Redis```实际使用的内存量（即 `used_memory`），但由于内存碎片的存在，```Redis```实际消耗的物理内存可能会超过此设置值，需防止溢出。通过设置此参数，可以在同一台服务器上安全地部署多个```Redis```进程，实现```CPU```和内存的隔离。

* 动态调整内存上限，```Redis```支持在不重启的情况下，通过 `config set maxmemory` 命令**动态修改最大可用内存**。
  *   **应用场景**：当某个实例内存不足而另一个实例有富余时，可以动态调整各自的上限以实现内存的弹性伸缩。
  *   **运维建议**：默认情况下```Redis```不限制内存使用，建议为所有生产环境的```Redis```进程配置 `maxmemory`，以防止极端情况下导致系统内存耗尽。

* 内存回收策略，```Redis```的内存回收机制主要通过两个方面实现：删除过期键和内存溢出控制。

  * 删除过期键对象，```Redis```采用**惰性删除**和**定时任务删除**相结合的机制：
    *   **惰性删除**：当客户端读取带有超时属性的键时，若已过期则执行删除并返回空。这种方式节省```CPU```，但若过期键长时间未被访问，会导致内存泄露。
    *   **定时任务删除**：```Redis```内部维护一个定时任务（默认每秒运行10次），采用自适应算法。它在每个数据库空间随机检查20个键，若超过25%的键过期，则循环执行。该任务有“快”、“慢”两种速率模式，以平衡回收速度与对正常请求的影响。

  * 内存溢出控制策略，当内存使用达到 `maxmemory` 上限时，```Redis```会触发溢出控制策略，由 `maxmemory-policy` 参数控制，共有6种策略：
    *  **noeviction**（默认）：不删除任何数据，拒绝所有写入操作并返回错误，仅响应读操作。
    *  **volatile-lru**：从设置了过期时间的键中，根据```LRU```算法删除数据。
    *  **allkeys-lru**：针对所有键，根据```LRU```算法删除数据。
    *  **allkeys-random**：针对所有键，随机删除数据。
    *  **volatile-random**：从设置了过期时间的键中，随机删除数据。
    *  **volatile-ttl**：根据键对象的 `ttl` 属性，删除最快要过期的数据。

    **性能影响与建议**：
      *   频繁触发内存回收（即 `used_memory > maxmemory` 时）会产生明显的计算开销，降低```Redis```性能。
      *   如果存在从节点，回收内存时的删除操作会同步到从节点，导致**写放大**问题。
      *   **运维提示**：建议线上环境确保 `maxmemory > used_memory`，以避免频繁回收带来的开销。若需快速回收内存，可临时调小 `maxmemory`，但这会导致数据丢失和短暂阻塞。
